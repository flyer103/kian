# v0.1.0 — first public release

First public snapshot of **Kian — the durable execution runtime for agents**.

A `Session` is the one first-class durable entity, the append-only event stream is the only truth, and
a `drain` is a disposable execution interval. Three promises follow from that shape.

![kill -9 mid-turn, no lost work](https://github.com/flyer103/kian-runtime/blob/main/docs/assets/durable-execution.gif)

## Durable execution

A crash, a deploy or a machine move costs a restart, not the work. Session state is a projection of
the stream, a new drain replays it and continues, and the exact model request bytes are persisted
before the call flies (`step/request`) — so replay is byte-identical and the provider's prefix cache
survives a takeover. Safety comes from epoch fencing, not from the lease: a partitioned-but-alive old
holder is fenced out.

The recording above is a real run: the turn is in flight, `kill -9`, a new drain takes over at
epoch 2, and the replay derives `2 of 2` request bodies byte-identically.

## BYOM execution

A single-binary `kiand` daemon runs the session's commands on the machine you choose, over a durable
at-least-once queue with a heartbeat watchdog, bound 1:1 to its worker session for that session's
whole life. Offline work parks and resumes; membership is liveness only, and binding is frozen for
the session's lifetime.

The same demo, recorded:
[the brain stays, the hands move](https://github.com/flyer103/kian-runtime/blob/main/docs/assets/byom.gif).

## Harness integration

The built-in ReAct loop, or dsh / Claude Code / Codex behind the same `LoopDriver` seam and the same
23 event kinds, selected **per worker agent**. A harness-owned loop is a *projection-only* session,
and the capability matrix states exactly what each one supports instead of implying equivalence.

## In this release

- **19 crates** — core, store (sqlite default, postgres for replicas), orchestrator and its bounded
  three-layer recovery, OpenAI-compatible provider with session-immutable model slots, the loop seam,
  memory, cron, hook plugins, endpoint/exec (KiandProto), the super-agent bundle, three harness
  bridges, the wire-only SDK, the CLI and the macOS iMessage bridge.
- **Contracts** — a 23-kind event model, a JSON-RPC + SSE API, `session inspect/replay/export`, a
  Prometheus `/metrics` surface, and a resumable read model.
- **Channels** — Lark IM, GitHub (webhook + poll), WeChat iLink (QR login, best-effort) and iMessage
  through a macOS bridge, with two-level admission filtering and untrusted-input marking.
- **Operational surface** — durable confirmation (`permissions: ask`), scheduled turns on a durable
  slot cursor, hook plugins over a stdio ABI, agent memory (notes + dreaming), and multi-replica
  safety.
- **An example** — [examples/issue-watch](https://github.com/flyer103/kian-runtime/tree/main/examples/issue-watch):
  a resident Router triaging one repository's issues, in one editable config.

## Getting started

Container, prebuilt archive, or source — the [README](https://github.com/flyer103/kian-runtime#install) has
one command for each. Then:

```bash
kian serve --config kian.yaml
```

`kian.yaml` and the RPC calls that run a session end to end are in the
[quickstart](https://github.com/flyer103/kian-runtime#quickstart); every other capability has one runnable
snippet in [docs/advanced.md](https://github.com/flyer103/kian-runtime/blob/main/docs/advanced.md).

## Boundaries, stated up front

- A projection-only harness session persists no `step/request`: durable control and audit, but no
  byte-level model-request replay.
- The BYOM command queue is at-least-once, not exactly-once; duplicate results dedupe on command id.
- No cross-worker failover: a binding is immutable, so moving to another machine means a new session.
- The WeChat channel is best-effort: iLink publishes no stable contract, and cross-downtime backfill
  is unmeasured.
