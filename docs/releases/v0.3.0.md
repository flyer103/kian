# v0.3.0 — iMessage attachments

An additive release: the iMessage channel now delivers what arrived, and a `kian` started under a git
hook stops pointing nested `git` at the caller's repository. No event kind, wire shape, replay rule or
database migration changes; a text-only payload keeps its exact bytes, and a config without `media:`
keeps its tool set byte-identical.

## Attachments reach the model

- **Metadata first.** The adapter models the bridge's `attachments` whitelist and maps `filename`,
  `mime_type`, `total_bytes` and `is_sticker` into the channel payload, so a photo, voice note or file
  arrives as `[image]`/`[attachment]` marker text plus what arrived instead of a bare marker. A
  text-only payload keeps its exact bytes (the key is absent without attachments), and
  `watch.attachments` (default on) documents the knob. One checked-in ABI row is asserted by both the
  bridge's emitter and the adapter's parser, so a renamed field fails a test rather than vanishing
  from the model's view.

- **Bytes are opt-in.** `attachments: bytes` (default `metadata`, refused without a `media:` section)
  fetches each image/audio item with the page's `generation` through the bridge's new authenticated
  `GET /v1/attachment` route, writes the bytes into the artifact store and hands the ADR-062 envelope
  to the media edge — the model reads an OCR/ASR transcript instead of a bare `[image]` marker. A
  generation mismatch is `409`, `watch.max_attachment_bytes` (default 16 MiB) bounds one file, a failed
  fetch keeps the metadata and admits the row, and base64 never persists. Vision of pixels stays out
  (ADR-063).

Contract: [CHANNEL-IMESSAGE §2.5, §3.2, §4](https://github.com/flyer103/kian-runtime/blob/main/design/CHANNEL-IMESSAGE.md),
[ADR-064](https://github.com/flyer103/kian-runtime/blob/main/design/decisions/ADR-064-imessage-attachment-bytes.md).

## Cron worktrees

A `kian` started under a hook (or any wrapper exporting `GIT_DIR`/`GIT_WORK_TREE`) no longer points
worktree inspection, creation or cleanup at that checkout instead of the configured repository: every
nested git spawn goes through `cron_worktree::git_command`, which scrubs the repository environment and
the object/store overrides.

## Upgrading

- No database migration, no event-kind change and no KiandProto bump (still v3): a `kiand` built from
  0.2.0 talks to a 0.3.0 `kian` and vice versa.
- The `kian` server must be upgraded for attachment metadata to reach the model: an older server
  ignores the additive field, so a mixed pair stays safe but the model sees a bare marker.
- The bridge must be upgraded for `attachments: bytes` (the new route); metadata mode works with the
  previous bridge.
- Enabling bytes is three config pieces, and the binaries go first: `attachments: bytes` on the
  channel, `media:` + `artifacts:` at the top level, and the media API key in the environment. An
  unknown `attachments` value refuses boot on the previous binary.

## Install

Prebuilt archives (with `.sha256`) for `x86_64`/`aarch64` Linux and macOS, and
`ghcr.io/flyer103/kian:0.3.0`. From source:

```bash
cargo build --release --locked -p kian-cli -p kiand
```

The macOS bridge is built from source (`cargo build --release -p kian-imessage-bridge`); it is not part
of the archives. The crates.io registry publish is a separate step.

## Boundaries, stated up front

- The WeChat channel does not emit the `media` envelope yet.
- `attachments: metadata` (the default) never fetches bytes; the model sees the name, type and size.
- The bridge route serves image and audio only; pixels do not reach the model as vision parts through
  this path (ADR-063).
